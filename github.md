## 6. Where work lives: issues, labels, milestones, `docs/bugs.md`

**The game repository's issues are the one task tracker, for both repositories.** An issue about the wiki carries `repo:wiki`; the wiki repository's own issues are only Michael's Verify stamps.

An issue is one piece of work a session can finish in one pull request: what, why (a link to the doc or ruling), what done looks like, and the guest's side if it touches the world. Big work (a spec like `docs/33`) becomes one issue per build step, linked from the spec. Ideas nobody has to decide yet live in `docs/05-someday.md` and one tracking issue, not one issue each (Michael, 2026-10-16).

**`docs/bugs.md` is the holding place for unverified bugs** (Michael, 2026-10-15): anything a session suspects but has not reproduced goes there, under Open, as a new line on the latest `main` (check Fixed and Closed first, so nothing closed comes back). **Once a bug is reproduced, the one who reproduced it opens an issue** (label `bug`, the steps to see it, linking the line) and moves the line to the file's "Became issues" section with the issue's number. A line that will not reproduce, or is intended, moves to Closed with a word why. Only reproduced bugs are worked as issues.

**Labels:** type `bug`, `feature`, `docs`, `art`, `chore`, `hotfix`; area `area:combat`, `area:multiplayer`, `area:world`, `area:items`, `area:building`, `area:ui`, `area:server`, `area:wiki`; `repo:wiki`; whose move `for:primary`, `for:secondary` (on issues; a pull request carries neither, its reviewer is always the other side); status `ready` (scoped, can be picked up), `in-progress`, `needs-review`, `changes-requested`, `needs-michael` (blocked on a ruling or an approval), `needs-playtest` (waits on Michael playing it in the game, not on a decision), `needs-wiki` (a merged or merging game change whose wiki update is not done), `blocked` (waiting on another issue, named in it). **Milestones** are the big items (`TODO.md` lists them with their issues); a milestone's page shows its progress.

## 8. The workflow: from an issue to `main`

1. **Pick it up.** Comment `Taking this. — <role>`, set `in-progress`. Work with no issue gets one first (it is the record of why).
2. **Branch.** From the latest `origin/main`, never from another branch: `git fetch origin && git switch -c <role>/<issue>-<slug> origin/main` (`secondary/57-farm-tilling`, `primary/64-ci-checks`). One branch per issue. **Nobody commits to the game's `main` directly**; Primary changes it only by merging a reviewed pull request.
3. **Build.** By `CLAUDE.md`: the two rules of shipping, the spec's build order, small commits with plain messages in the house style. Keep the branch fresh: merge `origin/main` into it whenever `main` moves, and always before asking for review. Push early (through `gh`'s credential while the bot is flagged): a pushed branch is visible to Primary and safe from a lost session.
4. **Prove it.** A change to what an item does (or a debuff) is read on its hover card in the pane, and the card fixed if it no longer tells the truth (Michael, 2026-10-20; `CLAUDE.md`, the hover card law). Before review, the author runs and records: `node --check` on every touched module; `node tools/check.js`; `node tools/world.js` (and `--roundtrip` if the save or the world changed), with the hash; `python -I tools/validate-data.py`; the spec's acceptance and the relevant `check()`s in the pane; for anything a guest touches, the two-tab test with `check("sync")` and the bytes it added to a frame. **The wiki:** a pull request in `cmz-wiki` for the pages the change touches, or the label `needs-wiki` so the wiki Secondary does it, or, for a change no player can see, one line saying so.
5. **Open the pull request.** `gh pr create --base main --title "<the change in plain words>" --body-file <file>`, or `--draft` while it is still moving. The body follows `.github/pull_request_template.md`: what and why with `Closes #<issue>`; how it was proved; the guest's side (the six points of `CLAUDE.md`'s multiplayer rule, by number, or "no world change"); the wiki; risks (the save format, `net.PROTOCOL`, the deploy, anything a merge would break for a friend mid-game); signed. Labelled `needs-review` and given its milestone; no `for:` label on a pull request.
6. **Review.** **The discussion happens on the pull request**, never in a chat. The reviewer reads the diff (`gh pr view <n>`, `gh pr diff <n>`), checks it out in its own worktree (`gh pr checkout <n>`, or `git worktree add`), runs the proofs itself, and plays it where the change can be seen. It comments on lines of the diff and ends with one review: `gh pr review <n> --approve --body "… — <role>"` or `--request-changes` once the bot is back (the box: a signed comment while it is flagged). On changes requested the author answers **each** comment (a fix in a new commit, or a reply saying why not), pushes, and asks again with `needs-review`. **No force-pushing a branch once review has begun.** **Who reviews whom:** Primary reviews every Secondary's pull request. Primary's own are reviewed by a Secondary: **a reviewing agent Primary starts for it** (a standing permission, Michael 2026-10-15: a fresh agent with no part in the change, signing `— Secondary (review)`; Primary answers its review in new commits and never signs a review of its own work), or a Secondary session Michael opens himself; or by Michael in the browser for anything `needs-michael` (he comments "Approved. — Michael" and Primary merges on it). **What needs Michael too** (label `needs-michael`; Primary does not merge without his word in the pull request): a change to a ruling or anything `docs/00` decides; the save format, `net.PROTOCOL`, or anything that can break an existing world (while every world is an expendable test, `02` 2026-10-17, a change that breaks an old save needs no word of his: the pull request says so in its Risks; Michael, 2026-10-17, on #153); the deploy, the server's storage, secrets, or the workflows; the rig's numbers and the drawing rules; deleting a doc or a feature; the files every session reads (`CLAUDE.md`, this file); anything Primary is unsure of.
7. **Merge (Primary).** When the review is approved (and Michael's word given where needed), the checks are green, the branch is fresh with `main`, and the wiki is done or labelled: Primary merges with a **merge commit** whose message is the house style's summary of what landed ("Merge #n, reviewed: …"): `gh pr merge <n> --merge --delete-branch --subject "…" --body "…"`. Then: watch the deploy (`gh run list --workflow deploy.yml`; the relay's front page names the new build); the issue closes itself; Primary ticks `TODO.md`, logs any ruling in `docs/02`, moves a fixed `docs/bugs.md` line where it belongs, and removes `needs-review`; `needs-wiki` stays on the merged pull request until the wiki Secondary's sync clears it.
8. **When something goes wrong in production.** **Revert first, fix second.** A merge that breaks the game for players is undone at once with a revert pull request (`git revert -m 1 <merge commit>` on a branch, label `hotfix`), merged by Primary without waiting for the usual review; the fix comes after, through the normal flow. **Never force-push `main`; never rewrite its history.** A hotfix takes the normal path with the review kept short; Primary may merge its own hotfix with Michael told in the pull request. Fly keeps its previous releases (`fly releases`); rolling the server back by hand is Michael's call.
9. **Releases and tags.** `main` deploys continuously, so a tag is a bookmark: when Michael plays a build with friends, or before a risky merge, Primary tags it (`git tag playtest-2026-10-15 && git push origin playtest-2026-10-15`, later semantic versions) and writes a release from the merged pull requests (`gh release create <tag> --generate-notes`). No tag exists yet. When the game ships on Steam (`docs/35`), tags become the release line.

## 10. Checks and protection

**CI on every pull request** (#1): `.github/workflows/ci.yml` in the game, its job `checks`, on pull requests, rerun on each push to the branch (the separate `push` trigger was dropped 2026-10-16: it ran every push twice): `node --check` on every `.js` under `src/`, `server/`, and `tools/`; `node tools/check.js`; `node tools/world.js` with `--roundtrip`, `--devchest`, and `--players=2` (the hash printed for the reviewer to compare with the pull request's claim); `python -I tools/validate-data.py`. The wiki builds with `--check` on every pull request in its own `check.yml`, which publishes nothing; `pages.yml` builds and publishes on a push to `main` (#3 asks for `--check` there too). The browser-only checks (`check("sync")` and the rest) stay the author's and the reviewer's in the pane: CI cannot open the game's window.

**Branch protection on the game's `main`** (Michael, Settings → Branches): require a pull request, require one approving review (**0 while the bot is flagged**, the box), require the CI check `checks` to pass with the branch up to date, block force-pushes and deletion. Michael keeps the admin's bypass for emergencies (a revert when no reviewer is free); Primary, on the same account, never uses it otherwise. On the wiki's `main`: block force-pushes and deletion only, so the wiki Secondary's syncs still push (section 9).
