## Step 1 — The loading shell

**What happens today, measured (2026-10-12):** `index.html` is a canvas and four hidden divs; nothing is visible until `boot()` (`src/main.js:660-891`) finishes. Boot awaits one thing after another: seven JSON files, every painted layer file, the map, then every sprite the map names (discovered by walking the map, `assets.loadMapSprites`), the build kinds, the held sheets, the player's figure (several hundred milliseconds of Canvas 2D), the dead and the villagers (a figure sheet per distinct outfit), the ground for the view and a ring (`ground.init`, `ground.prebake`), then the HUD and the title. **250 requests** (47 modules, 91 JSON, 111 PNG), DOMContentLoaded at 4.0 s and the last response at 15.5 s on a warm server; a cold pane has taken 15 to 45 s before `__game` existed. Everything in `data/sprites` is a request of its own; everything is `no-store` (`serve.py:23`), so a hard refresh re-downloads it all; a failure prints "boot failed: Failed to load image" with no stage and no file; the figure's canvases read pixels without `willReadFrequently` (`assets.js:390`, the console's warning).

**What is built.**

1. **The screen is HTML.** `index.html` gains `<div id="loading">` with the title, a bar (`<div class="bar"><div class="fill">`), a line of text, and a hidden error block with a Reload button; `style.css` styles it in the game's own colours (pillar 4 paints it later). It is visible at first paint, before `src/main.js` is fetched. `#stage` is hidden until boot reports done. The dead screen and the crash screen (step 2, A1) reuse this block.
2. **`src/boot.js`: a plan, not a function.** `export async function boot(stages, report)` runs `stages` in order; a stage is `{ name, weight, run(progress) }` where `run` may call `progress(fraction)` as it goes. The loader reports `{ stage, fraction, done, error }` to `report`, which drives the bar and the text, and records `timings[name]` in milliseconds on `window.__boot`. On a throw it stops, shows the stage, the file (every loader error names its path; `assets.loadJson` and `loadImage` already do), and the message in the error block, and rethrows. `?boot` in the URL prints the timings to the console and keeps the screen up until a click. The stages, in order, with their weights as a guess to tune: `manifest` 1, `data` 2 (items, build, combat, poses, loot, wardrobes, tuning), `art` 10 (every PNG and sprite definition in the manifest), `layers` 1 (every painted file), `map` 1, `figures` 6 (every outfit, below), `held` 2, `ground` 6 (the view and its ring), `world` 1 (chunks around the spawn, rooms, the light cache for those chunks, the first sight), `ui` 1. `main.js` becomes the list of stages and the wiring that was `boot()`; the game's state and step order move to `src/game.js` (step 2, D1, may happen here if the implementer finds boot easier to shape that way; say which in the commit).
3. **A manifest.** `data/manifest.json`, generated by `tools/manifest.py` (Python, like `serve.py`; no Node toolchain is introduced) from the folders: `{ "version": "<hash of every stamp>", "files": { "data/art/village/well.png": { "size": 1234, "stamp": "a1b2c3d4" }, ... } }` for every file under `data/` and `data/art/`, with `stamp` the first eight hex digits of the file's SHA-1. `serve.py` regenerates it on start and after every POST (the same function, imported from `tools/manifest.py`), so adding a file stays "add a file" plus a server restart or a save. The loader fetches `data/manifest.json` first (always `no-store`), then everything else as `path?v=<stamp>`; `serve.py` sends `Cache-Control: max-age=31536000, immutable` to any request carrying `?v=` and `no-store` to the rest. A hard refresh re-fetches the manifest and only the files whose stamp changed. Live edits still show: a changed file has a new stamp. The source files (`src/*.js`, `style.css`) stay `no-store`.
4. **Everything in parallel, bounded.** A `fetchAll(paths, limit = 12)` in `boot.js` (well under `serve.py`'s queue of 128) loads the manifest's files with a progress callback per file. `assets.js` learns to load from a list (`assets.loadAll(manifest)`) instead of discovering sprites by walking the map; `loadMapSprites` stays as a check that every sprite the map names was in the manifest, and throws with the name if not.
5. **Everything up front, as Michael asked.** Every sprite definition and PNG in the manifest, not only the map's. Every figure sheet an outfit in `data/wardrobes.json` can produce (`assets.sheetFor` for each wardrobe in both pools, plus the player's), so the first villager and the first turned villager cost nothing at the moment they appear. Every held sheet. The ground for the view and its ring (as now), and, new, the light cache (`light.chunkLight`) for the chunks around the spawn, the rooms (`map.rebuildRooms`), and the first sight, so the first frame is warm. Baking runs in slices with `await nextFrame()` between them (a `requestAnimationFrame` promise) so the bar moves and the page never freezes. `willReadFrequently: true` on every canvas that reads pixels (`assets.js:390`, the figure's packing, any in `figure.js`).
6. **The game starts behind the screen.** `#stage` shows and the title screen appears only when the last stage reports done. The loop starts then. Michael's law (`00`): people will sit for a loading screen if the game is good; the aim is honest stages, not a fast fake.
7. **`serve.py`, while it is open** (`23a`, section I): the cache headers above; an `Origin` check on POST (only `http://localhost:<port>` and `http://127.0.0.1:<port>`); a cap on `Content-Length` (8 MB) and a 400 on a bad header; the PNG magic bytes checked on a screenshot; the manifest regenerated after a save. The server must be restarted for `serve.py` changes to take (`CLAUDE.md`).

## Performance: how to tell what is cheap (Claude's answer to Michael's question, 2026-10-12)

**The atlas is a capacity limit, not a speed one.** All sprites are packed into one 4096 by 4096 texture (a 64 MB RGBA texture on the GPU and a 64 MB canvas copy on the CPU, both paid in full from the start) so the whole world draws with almost no texture switching. Running out means a new sprite does not fit (skipped with one warning; `gl.atlasInfo()` reads the fill: 42 percent on 2026-10-12). The fix is a taller atlas (8192 is 256 MB a copy, heavy for integrated GPUs) or a second page (a second texture and draw call: cheap). **The real cost is uploads:** whenever a sprite is placed or a sheet redrawn the whole canvas is re-uploaded (`gl.js`, `texImage2D` in `end()`), measured 1 to 14 ms for the full atlas against 0.2 to 4 ms for one sheet's rectangle (`texSubImage2D`): the fix when it matters; step 1's up-front baking means it happens at boot, not in play.

**A rule of thumb: is the thing a definition, an instance, or per-frame work?** *Definitions* (items, recipes, tags, loot tables, text) are data and cost almost nothing: thousands are fine. *Contents of a bag* are DOM nodes only while a panel is open: hundreds are fine. *Static instances* (a wheelbarrow, a crate, a station) are one quad each, drawn only in view: cheap. *New art* costs atlas space, a one-time upload, and boot time (one request per file; step 1's manifest and bounded batches are the fix). *Things that move, think, light, or update the DOM every frame* are the real per-frame cost, proportional to how many are near the player: the dead and villagers (AI, pathing, sight; the far dead stand still, and after step 2 the corpses cost nothing), **light sources** (each casts rays per chunk it reaches, and after step 2 only the chunks near a change rebuild), particles, and DOM overlays updated every frame (bars, bubbles; hundreds would hurt). GPU fill rate is not a concern for 2D sprites.

**Where the budget is (2026-10-12, the pane):** at the middle zoom the step is 0.2 ms, sight 0.2, render 0.3; at the wide zoom 0.5, 0.6, 0.5, with 67 dead and 158 drawables: **about fifteen times headroom in a 16.7 ms frame.** After a big addition, report the profile. For the big pass (`22`): stations, a wheelbarrow, tools, items, recipes, and seeds are the cheap kinds; the two to be deliberate about are light-emitting stations (a dozen in view is fine, hundreds is not) and the number of separate image files at boot, which the manifest makes a non-issue up to the server's queue.
