# 23 — The engine upgrade: robustness, the loading shell, the sprite system and its tool, the UI's look

**Status: scoped from Michael's brief of 2026-10-12, not built. A conversation doc: what is true today, what I propose, and the questions that decide the shape. Nothing here is a ruling until it is in `02`.**

Michael's brief: "make the engine more robust to support as much stuff on screen as can literally fit on a max-zoom canvas." Four pillars: **(1)** code quality, a senior's full review; **(2)** load speed, and a rebuilt shell that shows a loading screen instantly and loads everything, deliberately, behind it; **(3)** the sprite system and its editor, "a plane we were building as we flew it", with the goal of editing any sprite in the game from the tool and seeing it on a hard refresh; **(4)** organised menus and in-game UI with real art, a stone look like Minecraft's, with backgrounds so the UI is legible against the map.

The order I propose: **2, then 1, then 3, then 4.** The shell first because it is the thing the player sees every time, it is self-contained, and the review (1) is cheaper once boot is one well-shaped thing instead of a 100-line function. The review before the sprite work so the sprite work lands on code that has been straightened. The look last because it is art and polish, and because the review may move the UI code it would paint.

## Pillar 2 — Load speed and the loading shell

**What happens today, measured on Michael's machine (2026-10-12):** `index.html` is a canvas and four hidden UI divs; nothing is visible until `src/main.js`'s `boot()` finishes. Boot is one 110-line async function that loads **sequentially, one `await` after another**: seven JSON files, then every painted layer file (one request each, from `data/hair` and six `data/layers/*` folders), then the map, then every sprite the map needs (about 110 PNGs under `data/art`, in parallel at least), then it generates the held art, bakes the player's figure sheet (several hundred milliseconds of Canvas 2D), creates the dead and the villagers (each distinct outfit bakes another figure sheet), bakes the ground chunks for the view and a ring around it (`ground.init`, a second or more), and only then builds the HUD and shows the title screen. **The dark blank canvas is the whole of that time.** Two things make it worse: the preview server refused connections under the burst of requests (fixed once with a bigger listen queue, but a slow boot still shows "boot failed" now and then), and the figure baking runs `getImageData` hundreds of times (the console warning).

**What I propose: a loading shell that is up before the game exists.**

1. **`index.html` carries the loading screen in plain HTML and CSS**, no script needed to show it: the title, a bar, a line of text ("Baking the village...") in the game's own style (pillar 4 paints it later). It is on screen at the first paint, before `main.js` has even been fetched, so the page loads "instantly" because it does.
2. **A `boot.js` that is a plan, not a function.** Boot becomes a list of named stages with weights (`manifest`, `data`, `art`, `figures`, `map`, `ground`, `ui`), run by a small loader that reports progress to the bar and the text, and **fails loudly with the stage and the file** instead of the bare "boot failed: Failed to load image". Each stage can be timed, so the debug corner (or a `?boot` query) prints where the seconds go, and we tune what we measure.
3. **A manifest.** One generated `data/manifest.json` listing every file the game can ever need (sprites, art, layers, maps, data), built by a script in `tools/` from the folders (so adding an item stays "add a file"). The loader fetches the manifest once and then **everything in it in parallel, in bounded batches** (say 12 at a time, well under the server's queue), rather than discovering files by walking the map's sprite definitions. The game no longer learns what exists by trying to load it.
4. **Load everything up front, as Michael asked**, and bake up front too: every figure outfit the map's wardrobes can produce, every held item, every chunk the opening view and its ring need. The bake runs in chunks with `await` between them so the bar moves and the page never freezes. **`willReadFrequently: true`** on the baking canvases ends the warning and speeds the reads.
5. **The game starts behind the screen**: the title appears only when the last stage reports done, and the first frame is already warm (no ground baking at the first move, no figure baking when the first villager walks in).
6. **The rest is caching**: `serve.py` sends `no-store` on everything so edits always show, which is right in development but means a hard refresh re-downloads 110 PNGs. A version stamp in the manifest and normal caching for art would make a refresh fast without losing live edits (the stamp changes when a file does). This is the one that makes "hard refresh and see the edit" from pillar 3 work without a slow refresh.

**What this buys beyond the first impression:** a place to put the character creation screen (Michael's note: a shell rebuild was already wanted for that), a warm first frame, no mid-game baking stalls, and honest numbers. **What it costs:** the boot order is rewritten, `assets.js`'s discover-as-you-go loading is replaced by manifest loading, and the figure baking gets a chunked path.

**Questions.** Q2a: does a loading screen need to be skippable or is "it is fast enough that nobody asks" the target? Q2b: should saved games (the save system is still to come from the cozy parent) load behind the same screen? (I assume yes, one shell.) Q2c: a bar with stage names, or a bar alone? (I would show the stage names: they are honest and they are the debug output.)

## Pillar 1 — Code quality: the review

**The brief:** a senior engineer reviewing a junior's month of work for the first time, with lots of helpful criticism. **What I would do:** a written review first, as a document (`docs/23a-review.md`), file by file, before any code moves. Michael reads it, strikes what he disagrees with, and the fixes are then a checklist, not a mood. The review covers: what each module owns and where ownership leaks; the long functions (`boot`, `main.js`'s `update` at 150 lines, `tryAttack`, `entityDrawables`); the places state lives on the player object by convention (`attackCooldown`, `offCooldown`, `swingLock`, `exposedFor`, `blockFlash`, `offMemory`, `burnAcc`...) without a declared shape; the three ways a thing gets its numbers (a constant in a module, a block on an item, a block in `combat.json`), which should be one; copied-from-parent files whose headers say "unchanged" when they are not; the test story (there is none but scripts in the browser pane; a `tools/check.js` that runs the acceptance scripts headlessly against a fake DOM is possible and would make the regression passes repeatable); error handling (a failed image load is a console line and a black screen); naming and comment density; and dead code (the right-hold off-hand swing is gone, but its scaffolding?).

**What I know is already debt, so the review will not surprise anyone:** `main.js` is 880 lines and is the only place that knows the order of things; `interact.js` (1117) holds every verb in the game in one file; `figure.js` (1298) is the rig, the paper doll, the held art, the wardrobes, and the sprite generation; `placeholders.js` (1270) is every generated picture; `render.js` is the scene and the light textures and the overlays. None of these is wrong for a prototype; all of them are where a change touches more than it should. The review decides which to split and which to leave.

**Questions.** Q1a: does Michael want the review to propose a module layout (a target tree) or only to criticise what is there? (I would propose one; it is easier to argue with.) Q1b: how much refactoring is acceptable at once: a big-bang reorganisation between two commits, or a series of small moves each verified in the pane? (Small moves; the game must stay playable every evening.)

## Pillar 3 — The sprite system and its editor

**What is true today.** Three kinds of picture reach the atlas: **generated** (Canvas 2D code in `placeholders.js`, `figure.js`, `archery.js`, `fire.js`: the dev art), **drawn** (PNGs under `data/art`, described by `data/sprites/*.json`: anchors, frames, facings, slices, the village art from Claude Design, `17`), and **painted** (JSON pixel layers under `data/hair` and `data/layers/<slot>`, made in `tools/layers.html`, worn by the paper doll, `12`). The editor edits only the third kind, one slot of the figure at a time, and saves through `serve.py`'s `POST` (which accepts only those folders). The sprite definitions (anchors, frame rectangles, mirrors) are hand-written JSON; a wrong anchor is found by looking at the game.

**The goal, Michael's words:** edit any sprite in the game from the tool, save it back to the live game, see it on hard refresh. **What that needs:**

1. **One sprite model.** Every picture the game draws is a *sheet* with frames, anchors, and animations (that exists: `registerSheet`), and every sheet has a *source* that says how it was made: `{ generated: "well" }`, `{ drawn: "data/art/village/well.png", def: "data/sprites/well.json" }`, `{ painted: "data/layers/chest/tunic.json" }`. The editor opens any source; the manifest (pillar 2) lists them all.
2. **The editor grows three modes** on the one canvas it has (pencil, eraser, dropper, fill, parts and anchors already exist): **pixel editing of a drawn sheet** (open the PNG, edit, save the PNG and its def, with the anchor and frame boxes drawn over it and draggable); **painting a figure layer** (what it does now); and **"start from generated"** for any generated sprite (render the Canvas 2D placeholder into the editor, edit, save as a drawn sprite that replaces it: the path by which dev art becomes real art one sprite at a time, without Claude Design in the loop when Michael wants to do it himself).
3. **Save goes through `serve.py`** to any path under `data/art` or `data/sprites` or the painted folders (today the POST allows only painted folders), with the manifest's version stamp bumped so a hard refresh shows it (pillar 2's caching rule). Saving a PNG means encoding the canvas; the server writes bytes.
4. **A sprite browser**: a list of every sheet in the manifest with a thumbnail, filterable by kind, so "edit the well" is a click, not a path. The game's own atlas view (`gl.atlasInfo()` as a picture) belongs here too: see what is in the atlas and how full it is.
5. **Live preview in the game**: the editor already has the figure to preview on; for props, a small iso tile to stand the sprite on, lit by the game's own shader, would show anchors and heights honestly. (Or, simpler and good enough: save, and the game tab reloads itself on a message from the editor. Q3c.)

**Questions.** Q3a: is the goal a sprite editor (pixels) or also an animation editor (frame timing, facings, the swing poses in `data/poses.json`)? Poses have a Preview button in the editor today; a timeline is another thing entirely. Q3b: should the editor be able to edit the *definitions* (anchors, frames, mirrors) with handles, or only the pixels? (Handles; anchors are the thing that is wrong most often.) Q3c: hard refresh as the loop, or a live reload (the editor tells the game tab to reload a sheet)? Hard refresh is what was asked and is simple; live reload is nicer and is not much more once pillar 2's manifest exists.

## Pillar 4 — The UI's look: stone, backgrounds, organised menus

**What is true today.** The UI is DOM over the canvas (`#ui`, scaled by `view.js`), styled in one `style.css` of about 750 lines, grown row by row: the HUD stack bottom-left (moodles, health, stamina, hands text, clock), the swing bars bottom centre, the belt hotbar, the inventory panel, the context menu, the build palette, the screens (title, pause, settings, controls), the prompt, the speech bubbles, the floating bars, the debug corner. Panels have dark translucent backgrounds; the HUD bars sit straight on the map. Nothing has a frame or a texture.

**What I propose:** a **UI kit** before any screen is restyled: one stone frame (a 9-slice PNG: corners, edges, centre, so any panel size is the same picture), one inset well for bars and slots, one button in three states, one small set of type sizes, one palette (the stone greys, the gold of the swing timer, the orange of stamina, the greens and reds of health). Then every panel is built from the kit, which is what "organised" means in practice: the same frame, the same spacing, the same title style, from the title screen to the context menu. **In-game HUD elements get backgrounds** (the stone well behind the health and stamina stack, a stone strip behind the belt) so they read against grass and cobbles at every zoom. The kit is an **art request for Claude Design** (the way the village art came, `16` to `18`): stone frame, well, button, a few icons (the moodle glyphs are inline SVG placeholders today). Placeholders first, as always: a generated 9-slice (a grey stone tile with a bevel, drawn in code) so the layout work does not wait for the art.

**Questions.** Q4a: Minecraft's stone (flat grey, chunky bevel, pixel font) or something warmer that matches the village (the sibling's parchment-and-timber was once mentioned)? The reference decides the palette. Q4b: does the inventory grid (38 px cells, 11 px labels, Michael's sizes) change its look or only gain a frame? Q4c: a pixel font for the UI (there is none; the UI uses the browser's), and if so which: a free pixel font (there are good ones) or Claude Design draws one?

## What the upgrade is not

Not new features: no save system, no character creation screen, no crafting (those are `22` and the parent's saves). The upgrade is the floor those stand on. **The one feature that rides along** is the loading screen itself, because it is the shell.

## Build order, as steps for implementation

1. The loading shell: `index.html` with the screen, `boot.js` with stages, the manifest and its generator, parallel bounded loading, up-front baking in chunks, timings. Verified by the time from hard refresh to title and by the absence of baking stalls in the first minute of play.
2. The review document, then the agreed fixes as small verified moves.
3. The sprite model, the editor's three modes, the save path, the browser. Verified by editing the well's pixels in the tool and seeing it on a hard refresh.
4. The UI kit as placeholders, the panels rebuilt on it, then the art request.
