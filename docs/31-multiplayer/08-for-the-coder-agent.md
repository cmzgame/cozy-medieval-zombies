# 31.08 — Why every change is built for a guest: the reasoning behind the rule

**The checklist has one text: `CLAUDE.md`, "The two rules of shipping", the multiplayer rule. This page is the reasoning behind each of its six points; where the two differ, `CLAUDE.md` is the rule.** Since 2026-10-13 (Michael): multiplayer is live, and every addition and every change is built for it in the same commit. Friends play over the relay. Nothing is built for the host alone with the guest's side owed for later; letting it lag a week means a pile of catch-up work, and that is what the rule exists to prevent. The six habits the plan handed to the big pass's implementer before anything was built (ids on everything, one function for every entry, one mutator and one touch for every world change, verbs as a table, thin DOM handlers, the time scale on the world) are the floor these points stand on; they are facts of the code now, and their text is the record (`docs/history/31-multiplayer-record.md`, `08` as it stood).

1. **It runs in the world's step on the authority (the host), never in a DOM handler or a client-only module.** The host is the one place a change can happen for everyone; a DOM handler runs on one client, and a change made there is a world that differs on two screens. `main.js` only reads the world; what the host does beyond the step is `host.js`, which a server world runs too, with no window at all.
2. **A guest can do it through the same path the host's player uses:** a verb in `verbs.js`, a handler in `ui/inventory-actions.js` (a guest's call becomes a command by uid, slot, and bag address), a key event in the player's snapshot (`interact.keyEvents`), `placement.performPlacement`, or a `net.send*` command. Every target is an id, an address, or an entry's uid, because a guest's object is a copy and only a name reaches the host's. One path for both means the host's play and a guest's can never drift apart, and a guest's command is validated on arrival as the host's own click is.
3. **What it changes reaches a guest:** in the save, which is the welcome (`game.serialize`, `restore`), and in the frame (a player's light or heavy record, the delta of the dead with its roster, the pokes, the touched chunks, the stations' queues). The replica draws it as the host does. A guest sees only what travels: a field no frame carries and no save holds is invisible to a friend and lost on a rejoin. Whatever the host remembers of what it sent is forgotten when the thing leaves the world and at every welcome (`forgetSent`).
4. **World state it adds is in the sync check (`game.syncParts`),** or the reason it is left out is written beside the exclusion. `check("sync")` is the one test that says the wire is complete: every change that bypassed its mutator shows up as a part that differs, and a part the check does not hash can drift unseen.
5. **Per-player state lives on the player, never in a module-level variable; time comes from `loop.simTime()`, chance from `rng`.** A module-level variable means "the one player", which with friends is the wrong answer for all but one of them (the plan's audit found a dozen such singletons, every one of them since moved). Wall-clock time and `Math.random` make the host's world and the same save loaded elsewhere disagree, and the world hashes the same under Node (`node tools/world.js`) only because neither is read in the step.
6. **It is tried with a guest in two tabs** (`?nosave&mute&relay=none`, `__game.net.open({ join })`, both tabs stepped in turn) and `check("sync")` passes; the bytes it adds to a frame are read from `net.status().wire`, never guessed. The two-tab test is the only proof there is; a change nobody joined is a change nobody tested, and a frame's weight is measured because the plan's forecast of a few kilobytes a second was wrong by a factor of forty.

A spec names the guest's side of every feature as it names the host's. A review refuses a change that has only the host's.
